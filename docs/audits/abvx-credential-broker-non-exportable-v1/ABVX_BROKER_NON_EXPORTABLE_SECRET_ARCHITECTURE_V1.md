# ABVX Broker Non-Exportable Secret Architecture V1

**Chosen model: A — broker-internal Keychain access.** The Python broker calls macOS Security.framework directly through an in-process `ctypes` bridge. The production Swift subprocess helper with a `get` action was removed. The broker's supported socket operations remain `request` and `execute`; the credential is read only during an approved `openai.responses.create` operation and passed transiently to the fixed provider adapter. The supported CLI and IPC have no raw-secret return operation.

Flow: agent → owner-UID socket → pending request → interactive owner approval → scoped capability → broker `execute` → in-process `SecItemCopyMatching` → fixed provider operation → redacted result. The internal bridge has no executable entrypoint or IPC server. A normal invocation of its module with `get` arguments produces no output.

The SecItem bridge supports generic-password add/update/delete only for synthetic tests. The production CLI exposes no import or write command. The isolated-Keychain and default-Keychain synthetic lifecycles both passed create, update, internal use, delete and re-instantiation. The isolated test uses a temporary file-based Keychain; the default test uses a uniquely named synthetic service and deletes its item. Apple documents these [Keychain item operations](https://developer.apple.com/documentation/security/keychain-items). Apple [recommends the data-protection Keychain](https://developer.apple.com/documentation/security/ksecusedataprotectionkeychain) for new designs; this local proof uses the default file-based path, without claiming access-group isolation.

Authorization remains owner approval plus project, operation, model, purpose, budget, TTL and capability state. UID is a local constraint; PID/path are audit hints. An owner process with arbitrary Python execution could import the internal module or call Security.framework directly, and the same owner can edit state files. Those are explicitly accepted V1 owner-account limitations, not protected by this interface proof. No cryptographic agent identity is claimed.
